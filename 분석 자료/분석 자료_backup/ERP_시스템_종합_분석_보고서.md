# ERP 시스템 종합 분석 보고서 (문서 2-1 ~ 2-17)

본 보고서는 지금까지 정의된 ERP 세부 모듈(문서 2-1 ~ 2-17) 전체를 거시적인 관점에서 관통하며 분석한 결과입니다. 향후 실제 코드로 구현할 때 반드시 짚고 넘어가야 할 **공통화 포인트, 아키텍처적 주의점(Risk), 비즈니스 로직의 사각지대**를 다룹니다.

---

## 1. 프론트엔드 및 로직 공통화(Commonization) 포인트

여러 페이지에 걸쳐 파편화되어 작성될 가능성이 높은 기능들로, 사전에 **공통 컴포넌트(UI)나 Custom Hook(로직)으로 추출**해야 합니다.

### 1.1. 마스터 데이터 관리 UI 공통화
- **대상 모듈:** 고객사(2-3), 제조사(2-9), 공급사/Vendor(2-10)
- **분석:** 세 모듈 모두 `[목록 조회(Grid) → 검색 필터링 → 등록/수정 모달 → 삭제 Alert]` 이라는 동일한 CRUD 패턴을 가집니다.
- **해결책:** 개별 페이지를 일일이 하드코딩하지 않고, `<MasterDataGrid />` 및 `<EntityModal />` 형태의 공통 컴포넌트를 만들어 데이터 스키마(Schema)만 주입받아 렌더링하도록 추상화해야 합니다.

### 1.2. 검색 및 다중 필터링 로직 공통화
- **대상 모듈:** 입출고 내역(2-17), QA 검사(2-14), 생산 의뢰(2-12)
- **분석:** 날짜 범위(기간), 품목 검색, 거래처별 콤보박스 필터링이 산발적으로 등장합니다.
- **해결책:** `useMultiFilter(data, conditions)` 형태의 공통 커스텀 훅(Hook)을 설계하여 필터링 로직의 중복을 제거하고, 클라이언트 사이드 필터링과 서버 사이드 필터링(DB 쿼리)을 유연하게 전환할 수 있게 해야 합니다.

### 1.3. 상태(Status) 뱃지 및 파이프라인 라우팅
- **대상 모듈:** 발주 관리(2-13) ~ QA 검사(2-14) ~ 적재 관리(2-19)
- **분석:** `ORDERED` → `WAITING_INSPECTION` → `INSPECTION_COMPLETE` → `RECEIVED` 등 상태값이 모듈을 넘나들며 변합니다.
- **해결책:** 하드코딩된 문자열 대신 전역 `Enum`이나 상태 관리 맵(Map)을 선언하고, 특정 상태에 맞는 뱃지 색상을 반환하는 `<StatusBadge />` 공통 UI를 사용해야 일관성이 깨지지 않습니다.

### 1.4. '상세 보기(Detail View)' 패널의 단일 컴포넌트화 (Single Component Import)
- **대상 모듈:** 부품 상세 페이지, BOM 상세 페이지, 판매자(공급사/고객사) 상세 페이지
- **분석:** 수많은 페이지(예: 재고 현황, 입출고 내역, 발주 관리 등)에서 특정 부품이나 업체를 클릭했을 때 팝업/이동되는 '상세 정보 폼(Form)'의 레이아웃과 내용이 동일하게 반복 사용됩니다.
- **해결책:** `PartsDetailPanel`, `VendorDetailPanel`과 같은 **완전히 독립된 단일 컴포넌트(Single Component)**로 캡슐화하여 개발해야 합니다. 각 페이지에서는 이 컴포넌트를 단순히 `import`하여 불러다 쓰기만 하면 되며, 추후 상세 페이지 기능(예: 첨부파일 기능 등)을 수정할 때 단 하나의 코드 파일만 고쳐도 전체 ERP 시스템의 모든 상세 화면에 일괄 자동 반영되는 극대화된 유지보수성을 얻을 수 있습니다.

## 2. 아키텍처 및 DB 구조상 주의할 점 (Risks & Cautions)

현재 NoSQL(Firebase Firestore 등) 기반으로 시스템이 구동된다고 가정할 때 치명적인 데이터 무결성 문제가 발생할 수 있는 지점들입니다.

### 2.1. 데이터 동시성 및 원자성 (ACID 보장 위기)
- **위험 지점:** 입출고 내역(2-17) 기록과 재고(2-7) 실시간 증감, 부품 채번(2-1).
- **분석:** 여러 작업자가 동시에 같은 부품을 출고 처리할 경우, 재고(Inventory) 컬렉션 업데이트와 수불(Transactions) 컬렉션 Insert가 동시에 일어납니다. 만약 수불은 기록되었는데 네트워크 에러로 실재고 차감이 실패하면 장부가 틀어집니다.
- **해결책:** Firestore의 **Transaction API 또는 Batched Writes**를 강제하여, [수불 기록 + 재고 증감 + 발주 상태 변경]이 100% 한 번에 성공하거나 아예 취소(Rollback)되도록 백엔드 트랜잭션을 엄격히 설계해야 합니다.

### 2.2. 무한 재귀 호출과 BOM 폭발 (BOM Explosion)
- **위험 지점:** BOM 분석서(2-2), 생산 의뢰 백플러싱(2-12).
- **분석:** BOM은 트리(Tree) 구조입니다. 상위 조립품(Assy)을 1개 만들 때 하위 부품 10개, 그 아래 50개가 전개되는 구조인데, NoSQL에서 이를 재귀적으로 쿼리하면 엄청난 DB 읽기(Read) 비용과 성능 저하가 발생합니다.
- **해결책:** BOM을 매번 쿼리하지 않도록 **Materialized Path** 패턴이나 **Flattened Array**를 저장하여 한 번의 쿼리로 전체 구조를 가져오고 캐싱(Redis 등)을 적극 도입해야 합니다.

### 2.3. 입출고 트랜잭션(Transactions) 데이터 폭증
- **위험 지점:** 입출고 내역 분석서(2-17).
- **분석:** 회사가 성장할수록 수불 데이터는 무한정 쌓입니다. 이를 한 번에 브라우저로 불러오면 브라우저가 뻗거나 과도한 클라우드 과금이 발생합니다.
- **해결책:** 무한 스크롤(Infinite Scroll)이나 페이지네이션 쿼리를 필수 적용하고, 1년이 지난 데이터는 아카이빙(Archiving) 컬렉션으로 빼내는 백그라운드 워커가 필요합니다.

## 3. 비즈니스 로직 사각지대 (이상한 점 및 보완점)

기획 문서를 분석했을 때 실제 공장/영업 현장에서 발생할 수 있는 엣지 케이스(Edge Case)에 대한 대비가 부족해 보입니다.

### 3.1. 부분 입고 (Partial Receiving) 및 분할 검사
- **의문점:** 발주(2-13)에서 100개를 시켰는데 공급사가 오늘 50개만 보내고 내일 50개를 보낸다면?
- **개선 필요:** 현재 로직은 하나의 PO 문서가 `INSPECTION_COMPLETE`로 넘어가는 것처럼 보이나, 실제로는 **부분 입고**를 지원하기 위해 발주 원장(PO)은 `PARTIAL_RECEIVED` 상태로 두고, 50개짜리 QA 검수 큐(`receiving`) 문서가 쪼개져서 생성되는(Split) 분할 로직이 시스템적으로 정의되어야 합니다.

### 3.2. 생산 취소 및 자재 환원 (Reverse Backflushing)
- **의문점:** 생산 의뢰(2-12) 시 BOM에 따라 자재가 자동 차감(Backflushing)되는데, 작업 중 불량이나 오더 취소로 생산이 중단된다면?
- **개선 필요:** 차감된 자재를 다시 창고 재고로 돌려놓는 **'생산 취소에 따른 자재 환원(Reverse Transaction)'** 액션 버튼과 복구 로직이 기획에 명시되어야 합니다. 그렇지 않으면 재고가 허공에 증발합니다.

### 3.3. 이카운트 연동의 비동기 실패 처리
- **의문점:** 정산 관리(2-16)에서 이카운트 API로 세금계산서 데이터를 보냈는데 이카운트 서버가 점검 중이라면?
- **개선 필요:** 외부 시스템(API) 연동은 언제든 실패할 수 있습니다. 큐(Message Queue)에 담아두었다가 실패 시 재시도(Retry)하는 구조나, 사용자가 '수동 전송 재시도'를 누를 수 있는 화면 장치가 마련되어야만 재무 사고를 막을 수 있습니다.

## 4. 종합 결론 및 Next Step
현재 정리된 기획은 MSA 사상과 트렌디한 프론트엔드 구조를 띄고 있어 매우 훌륭한 청사진입니다. 다만 시스템이 코드로 전환되는 순간 "데이터의 정합성"과 "엣지 케이스 처리"가 발목을 잡을 수 있습니다.

따라서 코딩에 들어가기 전, 위에서 제기된 동시성 문제와 관계형 데이터 매핑을 완벽히 통제하기 위한 **[문서 3: 통합 데이터베이스 설계서 (ERD & 컬렉션 스키마)]**를 통해 각 모듈 간의 연결 고리를 물리적 DB 관점에서 단단하게 확정하는 작업이 가장 시급합니다.
